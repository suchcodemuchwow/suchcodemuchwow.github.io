## Too Many Props

### Smell

```tsx
<UserCard
  firstName={user.firstName}
  lastName={user.lastName}
  email={user.email}
  avatar={user.avatar}
  role={user.role}
  department={user.department}
  isOnline={user.isOnline}
  lastSeen={user.lastSeen}
  onEdit={handleEdit}
  onDelete={handleDelete}
  onMessage={handleMessage}
  onBlock={handleBlock}
  isEditable={canEdit}
  isDeletable={canDelete}
  showActions={true}
/>
```

### Why It Smells

- Hard to use and remember all props
- Indicates the component is doing too much
- Difficult to maintain and test
- Poor developer experience

| Prop Count | Assessment |
|------------|------------|
| 1-5 | Acceptable |
| 6-10 | Consider refactoring |
| 10+ | Definitely refactor |

### Refactoring Approach

```tsx
// Option 1: Pass objects for related data
interface User {
  firstName: string;
  lastName: string;
  email: string;
  avatar: string;
  role: string;
  department: string;
  isOnline: boolean;
  lastSeen: Date;
}

interface UserCardActions {
  onEdit: () => void;
  onDelete: () => void;
  onMessage: () => void;
  onBlock: () => void;
}

<UserCard
  user={user}
  actions={actions}
  permissions={{ canEdit, canDelete }}
/>

// Option 2: Composition
<UserCard user={user}>
  <UserCard.Actions>
    <EditButton onClick={handleEdit} />
    <DeleteButton onClick={handleDelete} />
  </UserCard.Actions>
</UserCard>
```

## Boolean Prop Explosion

### Smell

```tsx
<Button
  isPrimary={false}
  isSecondary={true}
  isOutlined={false}
  isGhost={false}
  isSmall={false}
  isMedium={true}
  isLarge={false}
  isDisabled={false}
  isLoading={false}
  isFullWidth={false}
/>
```

### Why It Smells

- Mutually exclusive booleans are confusing
- Easy to set conflicting values
- Verbose and hard to read
- Types don't prevent invalid combinations

### Refactoring Approach

```tsx
// Use union types for mutually exclusive options
type ButtonVariant = 'primary' | 'secondary' | 'outlined' | 'ghost';
type ButtonSize = 'small' | 'medium' | 'large';

interface ButtonProps {
  variant: ButtonVariant;
  size: ButtonSize;
  disabled?: boolean;
  loading?: boolean;
  fullWidth?: boolean;
  children: React.ReactNode;
}

<Button variant="secondary" size="medium">
  Click me
</Button>
```

<Callout type="info">
Keep booleans for true/false toggles. Use unions for one-of-many choices.
</Callout>

## Prop Drilling > 3 Levels

### Smell

```tsx
const App = () => {
  const [theme, setTheme] = useState<'light' | 'dark'>('light');
  return <Layout theme={theme} setTheme={setTheme} />;
};

const Layout = ({ theme, setTheme }: ThemeProps) => {
  return <Sidebar theme={theme} setTheme={setTheme} />;
};

const Sidebar = ({ theme, setTheme }: ThemeProps) => {
  return <ThemeToggle theme={theme} setTheme={setTheme} />;
};

const ThemeToggle = ({ theme, setTheme }: ThemeProps) => {
  return (
    <button onClick={() => setTheme(theme === 'light' ? 'dark' : 'light')}>
      {theme}
    </button>
  );
};
```

### Why It Smells

- Intermediate components don't use the props
- Changes require updating multiple components
- Tight coupling across the tree
- Unclear data flow

### Refactoring Approach

```tsx
// Context for truly cross-cutting concerns
interface ThemeContextValue {
  theme: 'light' | 'dark';
  toggleTheme: () => void;
}

const ThemeContext = createContext<ThemeContextValue | null>(null);

const useTheme = () => {
  const context = useContext(ThemeContext);
  if (!context) throw new Error('useTheme must be used within ThemeProvider');
  return context;
};

const ThemeProvider = ({ children }: { children: React.ReactNode }) => {
  const [theme, setTheme] = useState<'light' | 'dark'>('light');
  const toggleTheme = () => setTheme(t => t === 'light' ? 'dark' : 'light');

  return (
    <ThemeContext.Provider value={{ theme, toggleTheme }}>
      {children}
    </ThemeContext.Provider>
  );
};

// Components are now decoupled
const App = () => (
  <ThemeProvider>
    <Layout />
  </ThemeProvider>
);

const Layout = () => <Sidebar />;
const Sidebar = () => <ThemeToggle />;

const ThemeToggle = () => {
  const { theme, toggleTheme } = useTheme();
  return <button onClick={toggleTheme}>{theme}</button>;
};
```

## Giant useEffect

### Smell

```tsx
useEffect(() => {
  // Fetch user
  fetch(`/api/users/${userId}`)
    .then(res => res.json())
    .then(user => {
      setUser(user);

      // Fetch user's posts
      fetch(`/api/users/${userId}/posts`)
        .then(res => res.json())
        .then(posts => {
          setPosts(posts);

          // Update document title
          document.title = `${user.name}'s Profile`;

          // Track page view
          analytics.track('profile_view', { userId });

          // Set up WebSocket
          const ws = new WebSocket(`/ws/users/${userId}`);
          ws.onmessage = (event) => {
            const data = JSON.parse(event.data);
            if (data.type === 'status') {
              setOnlineStatus(data.status);
            }
          };
        });
    });
}, [userId]);
```

### Why It Smells

- Multiple unrelated concerns mixed together
- Hard to understand and debug
- Difficult to test individual behaviors
- Cleanup logic becomes complex

### Refactoring Approach

```tsx
// Split into focused effects
useEffect(() => {
  let cancelled = false;
  fetch(`/api/users/${userId}`)
    .then(res => res.json())
    .then(user => {
      if (!cancelled) setUser(user);
    });
  return () => { cancelled = true; };
}, [userId]);

useEffect(() => {
  let cancelled = false;
  fetch(`/api/users/${userId}/posts`)
    .then(res => res.json())
    .then(posts => {
      if (!cancelled) setPosts(posts);
    });
  return () => { cancelled = true; };
}, [userId]);

useEffect(() => {
  if (user) {
    document.title = `${user.name}'s Profile`;
  }
}, [user]);

useEffect(() => {
  analytics.track('profile_view', { userId });
}, [userId]);

useEffect(() => {
  const ws = new WebSocket(`/ws/users/${userId}`);
  ws.onmessage = (event) => {
    const data = JSON.parse(event.data);
    if (data.type === 'status') {
      setOnlineStatus(data.status);
    }
  };
  return () => ws.close();
}, [userId]);
```

<Callout type="info">
One effect, one purpose. If you're doing multiple things, split them.
</Callout>

## Many useState in One Component

### Smell

```tsx
const Form = () => {
  const [firstName, setFirstName] = useState('');
  const [lastName, setLastName] = useState('');
  const [email, setEmail] = useState('');
  const [phone, setPhone] = useState('');
  const [address, setAddress] = useState('');
  const [city, setCity] = useState('');
  const [state, setState] = useState('');
  const [zip, setZip] = useState('');
  const [country, setCountry] = useState('');
  const [isSubmitting, setIsSubmitting] = useState(false);
  const [errors, setErrors] = useState<Record<string, string>>({});
  // ...more useState calls
};
```

### Why It Smells

- State updates become verbose
- Related state can get out of sync
- Indicates component might be too complex
- Hard to reset all state at once

### Refactoring Approach

```tsx
// Option 1: Group related state with useReducer
interface FormState {
  values: {
    firstName: string;
    lastName: string;
    email: string;
    phone: string;
    address: string;
    city: string;
    state: string;
    zip: string;
    country: string;
  };
  isSubmitting: boolean;
  errors: Record<string, string>;
}

type FormAction =
  | { type: 'SET_FIELD'; field: string; value: string }
  | { type: 'SET_SUBMITTING'; value: boolean }
  | { type: 'SET_ERRORS'; errors: Record<string, string> }
  | { type: 'RESET' };

const initialState: FormState = {
  values: {
    firstName: '',
    lastName: '',
    email: '',
    phone: '',
    address: '',
    city: '',
    state: '',
    zip: '',
    country: '',
  },
  isSubmitting: false,
  errors: {},
};

const formReducer = (state: FormState, action: FormAction): FormState => {
  switch (action.type) {
    case 'SET_FIELD':
      return {
        ...state,
        values: { ...state.values, [action.field]: action.value },
      };
    case 'SET_SUBMITTING':
      return { ...state, isSubmitting: action.value };
    case 'SET_ERRORS':
      return { ...state, errors: action.errors };
    case 'RESET':
      return initialState;
    default:
      return state;
  }
};

const Form = () => {
  const [state, dispatch] = useReducer(formReducer, initialState);

  const handleChange = (field: string) => (e: React.ChangeEvent<HTMLInputElement>) => {
    dispatch({ type: 'SET_FIELD', field, value: e.target.value });
  };

  return (
    <input
      value={state.values.firstName}
      onChange={handleChange('firstName')}
    />
  );
};

// Option 2: Extract into custom hook
const useForm = <T extends Record<string, string>>(initial: T) => {
  const [values, setValues] = useState(initial);
  const [errors, setErrors] = useState<Partial<Record<keyof T, string>>>({});

  const handleChange = (field: keyof T) => (e: React.ChangeEvent<HTMLInputElement>) => {
    setValues(prev => ({ ...prev, [field]: e.target.value }));
  };

  const reset = () => setValues(initial);

  return { values, errors, handleChange, setErrors, reset };
};
```

## Deeply Nested JSX

### Smell

```tsx
return (
  <div className="page">
    <div className="container">
      <div className="content">
        <div className="section">
          <div className="card">
            <div className="card-header">
              <div className="title-wrapper">
                <h2>{title}</h2>
              </div>
            </div>
            <div className="card-body">
              <div className="form-wrapper">
                <form>
                  <div className="field-group">
                    <div className="field">
                      <label>Name</label>
                      <input />
                    </div>
                  </div>
                </form>
              </div>
            </div>
          </div>
        </div>
      </div>
    </div>
  </div>
);
```

### Why It Smells

- Hard to read and navigate
- Difficult to identify component boundaries
- Often indicates missing component extraction
- Makes maintenance painful

### Refactoring Approach

```tsx
// Extract meaningful components
const PageLayout = ({ children }: { children: React.ReactNode }) => (
  <div className="page">
    <div className="container">
      <div className="content">{children}</div>
    </div>
  </div>
);

const Card = ({ title, children }: { title: string; children: React.ReactNode }) => (
  <div className="card">
    <div className="card-header">
      <h2>{title}</h2>
    </div>
    <div className="card-body">{children}</div>
  </div>
);

const FormField = ({ label, children }: { label: string; children: React.ReactNode }) => (
  <div className="field">
    <label>{label}</label>
    {children}
  </div>
);

// Clean, readable component
const MyPage = () => (
  <PageLayout>
    <Card title={title}>
      <form>
        <FormField label="Name">
          <input />
        </FormField>
      </form>
    </Card>
  </PageLayout>
);
```

## Inline Functions Everywhere

### Smell

```tsx
const ItemList = ({ items }: { items: Item[] }) => {
  return (
    <ul>
      {items.map(item => (
        <li key={item.id}>
          <span onClick={() => console.log(item.id)}>{item.name}</span>
          <button onClick={() => fetch(`/api/items/${item.id}`, { method: 'DELETE' })}>
            Delete
          </button>
          <button onClick={() => {
            const newName = prompt('New name?');
            if (newName) {
              fetch(`/api/items/${item.id}`, {
                method: 'PATCH',
                body: JSON.stringify({ name: newName }),
              });
            }
          }}>
            Rename
          </button>
        </li>
      ))}
    </ul>
  );
};
```

### Why It Smells

- Hard to read with logic buried in JSX
- Can't easily test handlers
- Logic mixed with presentation
- New function instances on every render (usually fine, but can be problematic)

### Refactoring Approach

```tsx
const ItemList = ({ items, onDelete, onRename }: ItemListProps) => {
  return (
    <ul>
      {items.map(item => (
        <ItemRow
          key={item.id}
          item={item}
          onDelete={onDelete}
          onRename={onRename}
        />
      ))}
    </ul>
  );
};

const ItemRow = ({ item, onDelete, onRename }: ItemRowProps) => {
  const handleDelete = () => {
    onDelete(item.id);
  };

  const handleRename = () => {
    const newName = prompt('New name?');
    if (newName) {
      onRename(item.id, newName);
    }
  };

  return (
    <li>
      <span>{item.name}</span>
      <button onClick={handleDelete}>Delete</button>
      <button onClick={handleRename}>Rename</button>
    </li>
  );
};
```

<Callout type="info">
Extract handlers when they contain logic. Simple one-liners like `onClick={() => setOpen(true)}` are fine inline.
</Callout>

## String Refs (Legacy)

### Smell

```tsx
class MyComponent extends React.Component {
  componentDidMount() {
    // Legacy string ref
    this.refs.input.focus();
  }

  render() {
    return <input ref="input" />;
  }
}
```

### Why It Smells

- Deprecated API
- Not type-safe
- Can't be used in function components
- Performance issues with multiple refs

### Refactoring Approach

```tsx
// Function component with useRef
const MyComponent = () => {
  const inputRef = useRef<HTMLInputElement>(null);

  useEffect(() => {
    inputRef.current?.focus();
  }, []);

  return <input ref={inputRef} />;
};

// Or createRef in class components (if you must use classes)
class MyComponent extends React.Component {
  inputRef = React.createRef<HTMLInputElement>();

  componentDidMount() {
    this.inputRef.current?.focus();
  }

  render() {
    return <input ref={this.inputRef} />;
  }
}
```

## forceUpdate Patterns

### Smell

```tsx
class DataGrid extends React.Component {
  data: Record<string, unknown>[] = [];

  updateData(newData: Record<string, unknown>[]) {
    this.data = newData;
    this.forceUpdate(); // Force re-render
  }

  render() {
    return (
      <table>
        {this.data.map((row, i) => (
          <tr key={i}>{/* ... */}</tr>
        ))}
      </table>
    );
  }
}
```

### Why It Smells

- Bypasses React's state management
- Indicates data model issues
- Hard to debug and predict
- Usually unnecessary with proper state

### Refactoring Approach

```tsx
// Use proper state
const DataGrid = () => {
  const [data, setData] = useState<Record<string, unknown>[]>([]);

  const updateData = (newData: Record<string, unknown>[]) => {
    setData(newData);
  };

  return (
    <table>
      {data.map((row, i) => (
        <tr key={i}>{/* ... */}</tr>
      ))}
    </table>
  );
};

// If you need to trigger re-render without state change (rare)
const useForceUpdate = () => {
  const [, setTick] = useState(0);
  return useCallback(() => setTick(t => t + 1), []);
};
```

<Callout type="warn">
If you need forceUpdate, you're likely fighting React instead of working with it.
</Callout>

## Component in Component Definition

### Smell

```tsx
const Parent = () => {
  const [count, setCount] = useState(0);

  // Component defined inside another component
  const Child = () => {
    return <div>Count: {count}</div>;
  };

  return (
    <div>
      <Child />
      <button onClick={() => setCount(c => c + 1)}>Increment</button>
    </div>
  );
};
```

### Why It Smells

- `Child` is recreated every render
- Loses all internal state on parent re-render
- Causes unnecessary unmount/remount cycles
- Performance overhead

### Refactoring Approach

```tsx
// Move component outside
const Child = ({ count }: { count: number }) => {
  return <div>Count: {count}</div>;
};

const Parent = () => {
  const [count, setCount] = useState(0);

  return (
    <div>
      <Child count={count} />
      <button onClick={() => setCount(c => c + 1)}>Increment</button>
    </div>
  );
};

// Or if you need closure over parent scope, use render prop or children
const Parent = () => {
  const [count, setCount] = useState(0);

  return (
    <div>
      <Wrapper>
        {() => <div>Count: {count}</div>}
      </Wrapper>
      <button onClick={() => setCount(c => c + 1)}>Increment</button>
    </div>
  );
};
```

| Pattern | Re-renders | State Preserved |
|---------|------------|-----------------|
| Inner component | Every parent render | No |
| External component | Only when props change | Yes |
| Render prop | Every parent render | N/A (no component) |

<Callout type="warn">
Never define components inside other components. Always extract them to module scope.
</Callout>
